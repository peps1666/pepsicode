# 用户任务的生命周期与验收

这次改动参考了本机 dsh 的输入、轮次、目标与续行边界，沿用 Pepsicode 的 Python 执行器和有界验证循环。源码比较和改造前的离线探针见[审查记录](../archive/task-orchestration-review.md)。

## 从用户输入到任务结束

1. 每条用户输入有稳定的来源 ID。运行中的 `steer` 修改当前任务；`follow_up` 在当前任务通过验证后作为下一个独立任务执行。
2. 用户任务有独立的 ID、修订号、目标、验收条件和状态。一次用户任务可能经历多次模型请求、工具批次和验证重试；执行轮次结束不等于任务完成。
3. 新指令一经队列持久化接受，就增加当前任务修订号并清空旧证据。模型收到指令后才更新已交付修订号。验证必须对应同一个、已交付的修订号。
4. 项目回归检查和任务验收分别记录。只给计划、项目测试全绿、无文件变更、模型输出“完成”都不能替代操作类任务的验收条件。
5. 验收失败沿用有界修复：`maxIterations` 限制总轮数，`verificationNoProgressLimit` 限制重复失败；同时受执行取消、请求预算和费用预算约束。达到限制保持未完成。

任务类型包括 `answer`（解释、评审等回答）、`change`（实现或修改）和 `operation`（执行操作）。入口用文本规则初判，并记录原始输入、调用方指定类型及推断来源。所有任务在正常模型请求中获得任务视图，模型可用 `task_state classify` 携带理由纠正不确定的规则判断，无需额外分类请求。明确的操作类型和已识别的明确行动请求被锁定；“只解释”等限制不能通过分类升级变成执行授权。规则仍可能误判，覆盖样本不代表真实误判率已测量。显式验收条件即使用于回答类任务也必须检查。

## 可复核的验收条件

真实用户的新指令通过统一的 `task_intent` 投影修订当前意图，保留原始来源和历史。收紧为“停止修改，只分析”在接收时立即阻止新的修改；放宽为实现则等到消息和新意图在同一次会话保存中提交后生效。输入 ID 去重，撤回的待交付输入不会扩大范围，无关补充或“继续”不会取消旧限制。用户明确改为只分析后可结束为 `answered`，不将未做的旧实现宣称为完成。任务意图变化不会切换只读或 Plan 权限。

`task_state` 始终向主代理提供。`inspect` 返回任务和待回答问题；`define` 必须携带准确的 `task_id` 和 `revision`，只允许追加条件。条件包括：

| 条件 | 检查内容 | 证据 |
| --- | --- | --- |
| `file_exists` | 工作区内指定文件存在 | 路径、内容版本 |
| `file_contains` | 文件包含指定文本 | 路径、内容版本、是否匹配 |
| `file_absent` | 指定文件不存在 | 缺失版本；后续重新出现使证据失效 |
| `file_unchanged` | 与任务执行前宿主记录的内容版本相同 | 基线与当前版本；没有基线时不能通过 |
| `command` | 指定 argv 的进程成功退出 | argv、退出码、输出摘要与哈希 |

文件条件必须使用工作区相对路径。命令条件经过已有命令权限、Hooks、执行日志和取消路径，单条超时 30 秒。Python 字节码缓存按验收隔离，避免重复检查执行旧缓存。验收命令不会因为写在条件里而获得额外权限。

更新条件采用修订号比较。模型补充同一任务的验收条件时保留任务修订和已有 Worker 成果，归档旧验收，并按新的条件摘要重新验证。新用户指令仍使旧条件需要重新确认。若需求确实变化，`revise` 必须引用最新真实输入的 `instruction_id` 并说明原因，保存旧条件与修订依据。单纯“继续”不授权删除原条件。修改后的条件仍由模型解释用户意图，Harness 不能证明替换条件完整表达了用户的新要求。

一次验收生成 `acceptance_run_id`，将项目回归和任务条件绑定到同一任务版本、条件摘要、需求摘要与工作区内容摘要。准备阶段可用 `verificationPreparationCommands` 执行生成代码或 fixture 的命令；准备结束后才开始收集成功证据。最终在控制锁内复核内容、版本、必答问题、必需 Todo 和未知副作用。任一命令改变被验证输入，之前的绿色结果整体失效，返回 `verification_state_changed` 并在既有轮数上限内重验。

默认摘要读取源码、测试和配置等文件内容，跟踪新增和删除，不依赖 Git HEAD 或时间戳。`build`、`dist`、`release` 已纳入默认范围，不能仅因目录名称将执行代码排除。宿主固定排除 `.git`、依赖/虚拟环境、测试缓存、运行日志及宿主会话目录，不采纳模型传入的忽略规则。宿主配置 `verificationInputs`、文件条件及结构化需求只能扩大范围；显式目录递归读取，缺失路径也保留在 manifest 中。输入清单与排除策略摘要写入验收记录，策略变化使旧证据失效。

当前上限为 100000 个文件/目录条目、512 MiB，遍历不可读、范围越界或超过限制会阻止验收并提示选择对应项目/包作为工作区，扫描期间响应取消。仓库根目录包含大量历史 ZIP 等文件时也适用上限，不能静默排除这些目录再声称完整检查。执行快照中 `workspace_scans` 记录每轮扫描的原因、数量、读取字节和耗时；仅在同一次 manifest 构建内去重，不跨调用信任 mtime 或 watcher。完整规则在 `core/workspace_state.py`。

前后摘要是记录范围内的状态关联，不是文件系统或外部世界的事务快照；它不能抵御恶意进程“改动后还原”，未纳入范围的依赖和外部服务也可能变化。需要完整冻结时仍应在隔离副本或具备真实限制能力的后端验证。

条件可以提供 `input_id`、`purpose`；`criterion_sources` 记录调用方、结构化用户要求、规则推断或模型提出的来源。静态条件通过只报告“产物已检查，行为未验证”；命令条件通过报告声明的行为检查通过，不能推广为全部需求已被证明。聊天正文和执行轨迹都显示这种区别，验收数仅计算同一任务版本、验收轮次和工作区摘要的证据。

这些机制保证的是声明的条件确实执行并与相应任务版本关联。**条件是否覆盖全部需求，仍取决于调用方、模型和测试质量。** `file_contains` 适合产物检查；行为变更应优先使用针对行为的命令测试。文件存在和无关测试通过都不能证明功能正确。

程序调用示例（其余参数与原有 `run_verified_turn` 相同）：

```python
run_verified_turn(
    runtime=runtime,
    runner=run_agent_turn,
    model=model,
    tools=tools,
    messages=[{"role": "user", "content": "修复分页边界"}],
    cwd=workspace,
    permissions=permissions,
    task_kind="change",
    acceptance=[{
        "id": "pagination-behavior",
        "kind": "command",
        "argv": ["python", "-m", "pytest", "tests/test_pagination.py", "-q"],
    }],
)
```

WebSocket `turn/run` 同样支持 `task_kind`、`acceptance`、`task_requirements` 和 `answer_to`（问题 ID 数组）。`task_requirements` 格式为 `{"artifacts":["guide.md"],"behavior":false,"source":"user"}`；来源可为 `user` 或默认 `caller`。明确产物必须存在，其他已有文件不能替代；`behavior: true` 还要求针对行为的命令条件。来源由宿主入口设定，模型工具不能伪造。简单的文档/图片等具名产物可自动形成存在条件，仍只证明产物存在。

CLI/TUI/桌面共用这个入口。内嵌调用若要跨进程恢复，应使用 `recording_session(session)` 绑定持久会话；没有会话时只在 runtime 中维护状态。`runtime.taskAcceptance` 可设置调用环境的默认条件，多个不同任务应优先逐次传入 `acceptance`。

## 输入恢复与澄清

文件提及以 `file_mentions` 保存路径、来源输入、角色及推断依据。角色包括 input/output/delete_target/protected/reference；仅明确推断为输出的候选形成存在要求，不再要求迁移源或参考文件在交付时仍存在。`task_state correct_files` 接受 `file_roles: [{"path":"old.py","role":"input"}]` 和 reason，审计纠正推断；用户/调用方明确约束的修改仍须关联新的已交付指令。“出现文件名”及角色推断都不是语义正确性的证明。旧会话中的推断存在约束迁移为待复核提及，明确产物约束继续保留，旧证据留档。

原生入口将队列绑定到 `SessionData.task_control`。输入先落盘，再通知已接受；存储失败会回滚内存状态，调用方收到错误。交付采用 pending → claimed → 写入消息树 → acknowledge：崩溃后未进入消息树的 claimed 恢复为待交付，已进入消息树的输入按来源 ID 去重。

被移除或在停止时尚未处理的输入保存为 returned，界面将其退回草稿。恢复会话不会自动启动模型，也不赋予历史任务无限续行权限。下次显式运行才会继续处理恢复的队列；returned 可再次回显以避免丢失草稿。输入交付去重不等于外部副作用恰好执行一次，未知副作用仍须经过[执行恢复](harness-boundaries.md)核对。

Todo 和问题归属各自会话；子代理使用独立控制状态，不能修改父任务验收。Todo 有稳定 ID、完成状态和所属任务 ID。模型额外建议的可选工作可设 `required: false` 并记录 `reason`，未完成的可选 Todo 不阻塞交付；这不能删除明确需求或验收条件。`ask_user` 默认 `required: true`，任务进入 `waiting_user`；`required: false` 可提出不阻塞的问题。回复一个待答问题时可自动关联；多个待答问题应通过 `answer_to` 明确关联，系统不会用超时编造回答。

未完成任务收到“继续”，或等待澄清时收到回复，会保留任务 ID 并增加版本。普通新任务及 `follow_up` 创建新 ID，旧任务保存到历史。切换对话分支清除当前任务身份；复制或 fork 不复制任务续行身份和 inbox。重新生成同一任务仍必须重新验收，不能继承上一次成功结论。对话分支共用磁盘文件，不恢复历史文件状态。

## Worker 状态和交付

每次 `task` 调用分配独立的 `trace_id`，记录所属会话、发起步骤、分支、父任务及其修订。执行日志用执行范围 ID 关联实际请求和工具调用。宿主记录启动、模型和工具活动、审批、退出及中断。Worker 通过绑定到当前执行的 `agent_report` 提交独立的报告。该工具在 Plan 和只读模式下可用，其写入范围是父会话中的报告与问题元数据。

报告以执行 ID 和工具调用 ID 去重。报告和问题在一次会话保存中提交，必答问题沿用等待回复的轮次语义。回复带上问题 ID，修改父任务修订后重新计算等待状态。已结束的 Worker 保留原执行记录。主循环在下一次模型请求前，按稳定 ID 从报告和宿主结果生成有界内部通知，并在同一次会话保存中记录已交付的消息。通知经过常规模型请求构造及 `model/prepared` 记录路径。

会话快照保存关键转换。高频活动在内存按调用 ID 合并，随关键转换和会话检查点保存。保存取得会话锁后读取追踪快照。界面在锁外发送状态，WebSocket 的 `agent/update` 带会话 ID、序号和完整的第一页，客户端用 `agent/snapshot` 获取分页、详情或补取快照。两者都使用 Python 状态投影。分支切换保留原会话历史，fork 和 clone 开始独立的 Agent 记录。

慢连接只等待当前快照发送，期间的状态变化合并到下一份快照。桌面端每个会话同一时刻只补取一次首页。会话文件成功提交后会清除保存错误并更新追踪序号。

TUI 在界面线程消费相同投影，右侧状态栏自动显示并在运行中刷新耗时；窄屏改为输入区上方的状态摘要。侧栏优先显示当前分支中尚未结束的执行，只读取常驻记录，历史归档仍由显式分页查询加载。点击详情和翻页不触发模型调用。

Worker 每轮请求附带有界的剩余轮数提醒，按本轮循环余额和执行范围的请求配额取较小值，最后一轮要求交付已有发现及未完成事项。提醒仅存在于实际请求中，由提供者的 `model/prepared` 记录，不累积到会话历史。轮数与共享预算仍由既有执行入口约束；模型忽略提醒时仍会停止。`max_steps` 映射为 `budget_exhausted`，已有报告随不成功的工具结果交付，不能据此通过父任务验收。

会话常驻进行中的执行和最近 128 条已结束记录。更早的结果保存在同一个会话文件，历史查询按需读取。每次执行最多保存 64 份报告和 8 条最近的工具预览。

重启后，缺少存活依据的运行状态标为中断待核对。执行日志仍是未知副作用的权威来源，核对沿用执行恢复流程。WebSocket 断开会取消该连接的活动轮次，重新连接需恢复原会话才能读取历史。

## 结束原因与防空转

内核另有一个编排宿主原型，位于 `pepsicode/orchestration/runtime.py`。它先取得会话所有权再加载快照，随后按工作区真实路径取得独占锁，提交启动领取后才调用宿主提供的执行器。使用同一系统临时目录的其他调度实例遇到同工作区争用时直接返回错误。锁覆盖调度与回调全过程，只约束通过该入口运行的宿主。单个调度实例内，仅宿主判定为只读的工作可以并行。

结果和待协调事件同批保存。宿主可在其他执行仍运行时处理该结果并添加后续工作。恢复时按有界批次提供仍待投递的当前修订结果，每批确认后再提供下一批。旧修订的结果保留在尝试记录中。重启发现未结算的领取时暂停投递和派工，保留待核对记录；存储层同样拒绝新的启动领取。

宿主可通过 `run_pending(..., coordinate=..., start_turn=True)` 显式发起初始协调回调。回调收到当前会话、包含 `task_dispatch` 和 `agent_status` 的工具注册表及事件来源尝试 ID。初始回调的尝试 ID 为 `None`。派工根据当前任务修订原子保存，成功后立即返回预留的工作、尝试和追踪 ID。`agent_status` 从持久快照分页读取当前父任务的队列及结果，可按追踪 ID 查询。结果回调可先调用 `deliver_pending` 持久化事件输入，再把更新后的历史交给协调模型。派工工具随回调结束失效，Plan 和只读权限禁止派工。

宿主可以通过 `run_pending(..., worker=WorkerExecutor(...))` 接入现有子 Agent 执行入口。它使用派工时预留的追踪 ID，复用 `agent_report` 和现有工具过滤，并让协调回调与 Worker 共用同一根执行范围的预算、日志、截止时间及全局取消。只允许 Explore Worker 并行，其他 Worker 持有排他名额。托管 Worker 仍通过现有进程执行层运行前台命令，持久后台命令在启动前被拒绝。

必答问题由 Worker 原子保存到父任务的提问记录。该尝试收尾后产生 `waiting_user` 结果事件，协调者可在兄弟 Worker 仍运行时处理。全局停止禁止新派工启动和协调唤醒，已启动的 Worker 按执行层取消并收尾，未领取的当前任务派工保存为已取消。未知副作用保留在执行日志与未结算领取中。

TUI、桌面和 QQ 共用的 `run_verified_turn` 读取 `orchestration.enabled`，启用时将模型轮次交给编排宿主，任务验收仍使用原有入口。用户补充指令通过现有队列唤醒协调者，旧修订后续副作用继续由执行层拒绝。包含受信任命令 Hook 的宿主串行使用工作区，并在释放前等待这些 Hook 收尾。

并发与事件节奏由 `orchestration` 段显式配置并经启动校验：`maxConcurrentWorkers`、`maxQueuedWorkItems`、`maxActiveWorkItemsPerRun`、`maxAutoRetries`、`maxCoordinatorActivations`、`eventBatchLimit`、`eventContextChars`、`eventDebounceMs`/`eventMaxDelayMs` 和 `coordinatorReserveRequests`。默认值与用户说明见[功能指南](../guides/features.md#异步编排)。

编排宿主在协调轮次边界先提交队列中的用户指令和定向回复，再按已交付的任务修订绑定工具。轮次中途入队的输入交给下一轮。即使输入在交付后、工具绑定前入队，当前轮也只能使用已交付的修订，新的派工由存储层拒绝直至下一轮接收输入。

协调者可以在派工前后补充同一任务的验收条件。有当前修订的 Worker 排队或运行时，协调者发出进度消息并结束模型响应后，宿主接管调度与唤醒。

交互协调者在共享或 `workspace` 模式下可以直接使用主工作区的文件和命令工具来完成普通需求，修改计入主任务验收。已派工的任务转入协调流程，运行中的 Worker 与主工作区直接写入分开调度。`hardened` 保留原有 Worker 执行入口。

交互派工时模型明确选择整个任务的交付物。首次成功派工将 `project`（项目交付）或 `worker_reports`（收集各自结果）绑定到当前修订。调用方的显式产物或行为要求始终需要项目验收。在收集结果的任务中，宿主保存每个 Worker 的完成事件，等同批其余工作结束再唤醒协调者。失败、阻塞和必答问题仍及时投递。结果消息携带 checkout 路径；完成证据记录 Worker 报告及其归属，恢复时复核持久记录。

`task_cancel` 持久化单次尝试的停止请求，再向该 Worker 发出局部取消。`task_note` 可给未启动尝试补充有界上下文。`task_retry` 在当前修订和预算下为可重试的调查失败或已获定向回复的任务建立新尝试；失败实现类尝试按修复分类与指纹重试，新尝试在核对受管 worktree、分支与提交归属（HEAD 线性接续已记录基线）后接续同一工作项已确认的提交成果。Worker 结束时的最终结构化报告决定结算结果：明确 `failed`/`blocked` 按该结果投递事件，报告附带有界结构化证据（阶段、失败类别、失败检查、输出摘要、日志引用）供修复分类与指纹使用。旧尝试保留原 ID 和结果。

集成验收失败后，同一任务修订内新派发的实施尝试默认从失败集成记录的 head 准备工作区（manifest 记录 `base_integration`）；父任务的验收条件与必需产物在已交付的集成 checkout 上检查，绑定当前修订、干净 checkout 的 HEAD 与交付记录，交付版本变化后按新版本重验。

托管运行把任务预算绑定到持久化执行日志。恢复时从实际提供方请求记录重算请求数及可确认费用，金额预算遇到不确定用量会停止继续请求。中断的领取进入待核对状态。用户明确发送“继续”后，宿主在确认日志没有未核对操作时关闭旧尝试并恢复协调。仍有未知操作时提供现有 `execution_status` 核对入口。

`task_dispatch` 的工具调用身份、已接受的尝试和启动动作在同一次会话保存中提交。显式继续时，如果日志缺少工具回执，宿主只在调用身份和派工参数与持久记录匹配时确认该派工，保留原尝试和当前修订。已领取的尝试与其他未知操作仍需各自核对。

### M2 工作区准备

`prepare_environment` 是宿主准备入口，接收当前排队的实施 WorkItem、明确的提交 SHA 和执行范围。它按工作 ID 在 `.pepsi-code/m2/` 下分配 checkout 与运行目录，使用 `codex/m2-<work_id>` 分支。Git 操作经过进程执行入口，目录创建经过文件执行入口。准备时持有会话、工作区及 Git 公共目录的协作锁，并保存仓库身份、提交、分支和准备阶段。

准备以提交内容为基线。主目录的未提交改动、未跟踪配置与依赖目录留在主目录。准备入口禁用 checkout Hook，并使用最小化的 Git 子进程环境。失败时保留现场和日志，重新打开时核对公共 Git 目录、分支、HEAD 与运行目录。

将 `orchestration.workerIsolation` 设为 `workspace` 后，共用编排入口会在领取实施任务前自动准备独立工作区，并使用独立 Worker 进程：工作区是具备有效 `HEAD` 提交的 Git 仓库根目录时，使用 Git worktree（基线是准备时的已提交 HEAD）；工作区为空目录、非 Git 目录或尚无首次提交的仓库时，自动准备目录级隔离工作区（`workspace_kind: "directory"`，在 `.pepsi-code/m2/<work_id>/checkout` 下复制有界基线文件或建立空目录，同样支持并行执行、结果汇总与无冲突本地目录集成/交付；推送分支与开 PR 仍要求 Git 仓库）。默认 `shared` 保留 M1 调度。`orchestration.workerTimeoutSeconds` 控制受管 Worker 进程的墙钟上限（默认 300 秒），进程异常退出时会附带有界 `stderr` 摘要。

`hardened` 模式仍要求工作区为具有有效 `HEAD` 提交的 Git 仓库根目录并在入队前检查。只读调查和共享工作区派工可在普通目录执行。

`hardened` 使用 Linux [Bubblewrap](https://github.com/containers/bubblewrap)。准备时需用真实子进程检查命名空间是否可用，失败会阻止 Worker 启动。Worker 的命令在隔离环境中运行，只挂载 checkout 和所需的只读系统程序、运行库，清除继承环境并隔离网络。宿主代理的工具限于工作区读写和受管进程，共享 Git 管理目录留在宿主。Windows 仍拒绝 hardened 请求。CPU、内存及 checkout 总磁盘配额尚未实现。

### M2 受管进程通道

`run_worker_process` 是宿主侧 IPC 入口。它使用执行层批准启动受信任的子进程，通过专用标准输入输出管道交换 JSON 帧。宿主核对运行、尝试、代次、连接随机标识和连续序号，并拒绝超长帧、超量消息和未注册操作。子进程只请求宿主明确注册的处理器，处理器在同一子执行范围内使用宿主预算、权限与日志。

通道记录 PID 和退出码，观察子范围取消及截止时间，并回收进程树。准备好的实施任务使用独立 Python 子进程推进模型和工具轮次。IPC 只传轮次指令，实际消息历史、模型凭据、工具调用参数及执行结果由宿主持有。宿主依据自己收到的模型响应执行对应工具批次，并沿用提供方请求日志、共享预算与工具审批。

宿主的路径解析将 Worker 的文件访问与进程工作目录限制在其 checkout 内。`workspace` 级命令使用该 WorkItem 的临时目录和缓存路径，经批准的程序拥有当前 OS 用户权限。`hardened` 命令使用命名空间内的临时目录、清理后的环境和独立网络命名空间，共享 Git 元数据留给宿主处理。进程通道提供截止时间和 IPC 配额，当前子进程入口要求源码 Python 运行时。

桌面、QQ 和终端服务控制台在认证时发送 `orchestration: 1`。旧 WebSocket 客户端在交互模式沿用同步轮次，在启用异步编排的常驻服务上会收到升级提示。TUI 的进程内入口直接读取配置。`agent_status` 查询已保存状态，`task_request_report` 为当前已结束的 Worker 结果排队一次只读澄清，使用当前任务的请求额度。

### M3 常驻服务模式

`pepsicode/service/` 提供独立于 TUI/Electron 的常驻服务进程。`python -m pepsicode.service start` 以分离进程启动，`stop`/`status`/`health` 查询或停止，`foreground` 是供 NSSM/systemd 等服务管理器直接调用的前台入口。服务身份（PID、运行代次、端口、令牌指纹）与人工停止标记持久保存在 `<workspace>/.pepsi-code/service/`。存在存活 PID 时拒绝二次启动；`service/shutdown` 写入人工停止标记，之后外部守护程序的普通 `start` 会被拒绝，只有人工 `start --clear-stop` 可以重新启动。

服务模式下会话由 `ServiceHost` 持有。客户端连接通过 `session/create`/`session/resume` attach 到驻留会话，断开只解除订阅：不设置取消事件、不拒绝待审批请求、不销毁工具。同一会话同时只允许一个控制连接，第二个控制器被明确拒绝。`connection/ready` 携带 `service`、`execution_mode` 与代次标识，旧客户端忽略这些增量字段。`connection/auth` 令牌沿用现有鉴权，服务只绑定回环地址。

关键事件（message/end、turn/end、permission/request、verification/update、input/queue 等）按会话持久写入事件日志。重连的客户端从 `session/resume` 返回的 `event_cursor` 之后，通过 `session/events` 按游标补取离线期间的事件；高频流式增量不入日志。断开后到达的审批走 `ServiceApprovalBackend`：预授权策略明确覆盖的命令与路径自动允许并记录，其余拒绝并合并写入通知发件箱，不会伪装成普通模型错误，也不会静默重试。

预授权策略保存在 `<workspace>/.pepsi-code/service/policy.json`，字段严格校验（未知字段即报错），记录用户、工作区、允许路径、允许命令前缀、外部动作、费用/次数/时长上限、有效期与撤销状态。`service` 模式的 `turn/run` 要求策略生效；撤销与到期在每次检查点（审批入口、轮次入口）从磁盘重新加载后立即生效。未配置或失效策略时服务拒绝接受无人看护任务，不采用全局跳过审批。

外部事件连接器（`pepsicode/service/connectors/`）由宿主侧 Python 轮询，协调模型不轮询外部 API。GitHub 连接器只读拉取 PR 审查与 check runs，令牌取自环境变量（不入配置文件和日志）；外部事件 ID 持久去重，事件绑定仓库与 head SHA，来源仓库必须在允许列表内。事件只会作为 steer 输入进入活跃的协调轮次或暂存为待处理输入并发送合并通知，它们不新增授权、不自行启动轮次。

`service/health` 与 CLI `health` 返回分项健康：存储（事件日志写失败会暂停新的轮次）、队列（编排排队/执行/等待回复计数）、模型、Worker、连接器（含最后错误与退避）、通知（发件箱积压与不确定计数）。快照周期写入 `health.json`，CLI 不依赖 WebSocket 即可读取。`notifications/fetch {cursor}` 供控制端补取离线通知，按任务/问题/交付版本去重，发送结果未知标记为 uncertain，不自动重发。

服务重启后，`session/resume` 重新加载会话；预授权策略有效且编排 effect 全部 pending 时，attach 会驱动与用户“继续”相同的续行路径。服务启动时还会扫描本工作区的持久会话并按同样条件无头续行（不依赖任何客户端接入，顺序执行以避免工作区编排锁争用）；存在已领取或待核对 effect 时仍等显式继续，不自动重放，并写入合并通知。旧进程代次无法结算或重放新宿主的领取（沿用编排存储的代次围栏）。`orchestration.executionMode` 配置为 `service` 表示服务持有运行，客户端不能通过 RPC 切换模式。桌面端通过 `PEPSICODE_SERVICE_URL` 与 `PEPSICODE_SERVICE_TOKEN_FILE` 环境变量接入常驻服务：主进程不再生成（退出时也不再终止）自有后端，渲染层依据 `connection/ready` 的服务标识显示“断开连接不会停止任务”，待处理通知计数来自 `notifications/fetch`。远程部署、服务账户与凭据轮换需要操作者自行部署与审计；关闭笔记本后任务是否继续取决于服务所在主机是否在线。

普通与流式模型响应都检查停止原因。`max_tokens`、`pause_turn`、拒答和缺少完整结束事件不会被当作最终成功，也不派发该响应里的工具。已有的空推理输出重试仍有次数上限；非空的半截结果只作为过程保留。流式响应即使出现 `end_turn`，缺少最终 `message_stop` 仍视为不完整。

共享验证循环默认最多重建一次可恢复的截断/传输失败请求，可用 `modelRecoveryLimit` 设置为 0 禁用；重建占用同一个总轮数和请求预算，不拼接工具参数。费用不明、未知副作用、取消和权限拒绝不能借此重放。费用不确定标记随执行状态保存，下一轮也不能把缺失用量当成零。失败原因分别引导补条件、修复检查或稳定验证输入；有任务相关代码/条件的状态时，仅改变日志不会重置无进展计数。

不完整结果携带 `recovery.reason_code` 和 `next_action`。明确“继续处理当前任务”保留原任务身份并重新验收，不直接重放选中的命令。恢复旧会话会重新比较证据的条件和内容摘要；无法证明仍有效时保留历史记录，将当前结果标为待复核。

同一执行范围内，相同任务版本、工具、参数和结果连续重复时，默认在第 3、5、8 次附加提醒，要求改变方法或说明阻碍。可设置 `repeatToolThresholds: [3, 5, 8]`，必须为递增且不重复的整数，最小为 2。提醒不扩大权限，也不替代预算和修复轮数限制。

任务状态为 `active`、`answered`、`complete`、`incomplete`、`waiting_user`、`cancelled`、`blocked`、`unknown` 或 `budget_exhausted`。桌面轨迹显示任务状态和已满足条件数，服务端 `turn/end` 返回任务报告；执行成功与用户任务未完成可以同时存在。

当前实现提供有界重试、显式继续和持久恢复，没有新增跨进程无人值守的无限目标驱动器。离线编排回归见 `tests/core/test_task_orchestration.py`；真实任务评测入口和 smoke/real 统计边界见[任务评测](../development/task-evaluations.md)。
