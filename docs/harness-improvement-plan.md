## 1. 验收证据必须对应最终被交付的状态

**优先级：P0；证据 A。**

修改位置：`core/task_verification.py`、`core/verification.py`、`execution/filesystem.py`；新增一个供两类验证共用的状态指纹模块。

- [x] 为一次验收生成 `acceptance_run_id`；记录任务 ID、任务修订号、条件集合摘要和被验证工作区状态摘要。
- [x] 状态摘要必须包含被验证源码、测试、项目配置的内容，以及新增和删除。不能只依赖工具的 `mutation_count`、Git HEAD 或文件时间戳。
- [x] 定义由宿主实现控制的快照范围和排除规则。缓存、日志等可排除；模型不能自行把源码或测试声明成“缓存”绕过检查。大仓库先测摘要开销，再做增量优化。
- [x] 把生成代码、准备 fixture 等允许改变被验证输入的步骤移到验证准备阶段；准备结束后才开始积累成功证据。
- [x] 项目回归与任务验收共用状态标识。命令运行导致相关输入变化时，之前的相关证据失效，不能仅以该命令退出码为零保留绿色结论。
- [x] 完成前重新核对状态、任务修订号、未回答必答问题、必要工作项和未知副作用；在控制状态锁内提交判定。条件内容变化也必须能使旧证据失效。
- [x] 为验证期间持续改动设置有限重试；停止时返回 `verification_state_changed` 等结构化原因。
- [x] 第一版采用运行前后内容摘要核对；后续可在隔离副本或具备真实限制能力的后端中验证。文档明确前后摘要不抵御恶意进程“改动后还原”，也不是整个外部世界的事务快照。

验收：先检查 `VALUE == 42`，随后命令改成 `0`，不得通过；源码被删除或新增后旧证据不得沿用；正常测试写入合法缓存不造成无限重验；用户中途改需求不得提交旧版本成功。

自审：仅“最后再跑一次”仍可再次修改代码；仅禁止命令工具的写参数也约束不了测试内部写入。采用状态关联、变化失效和有限重验更可落地。

**实施证据：** `core/workspace_state.py`、`TaskVerifier.verify`；覆盖后续命令破坏旧绿结果、同时间戳内容变化、新增/删除、缓存排除、显式生成物覆盖及准备阶段。快照范围和非事务限制见 [生命周期文档](task-orchestration.md)。

## 2. 任务识别与执行权限分开，补齐行动请求漏判

**优先级：P0；证据 A。**

修改位置：`core/task_control.py`、`core/agent_loop.py`、`tools/task_state.py`、CLI/TUI/服务端输入入口。

- [x] 原始用户输入、显式 `task_kind`、规则推断和模型修正分别记录来源，便于定位误判。
- [x] 保留规则作为低成本初判，增加中英文、口语、省略句及混合请求样本；不把持续堆关键词作为唯一机制。
- [x] 首次正常模型请求即可纠正任务类型，不为每条输入额外发一次分类请求；向所有任务提供简短任务视图，回答类也能看到当前判断。
- [x] 区分修正规则误判与削弱明确行动请求。调用方明确指定的行动类型、用户明确要求的工作不能被模型降级跳过；纯规则误判的纠正记录依据和版本，并覆盖“解释怎么修复”这类含行动词的问答。
- [x] 在明确实现目标的上下文中出现写文件、运行实现命令等行为时，触发任务契约复核。工具影响由宿主定义，不能只信任模型声明；纯元数据或计划文件写入不能简单等同于实现任务。
- [x] 对“先解释再修改”等混合请求保留需要执行的部分；回答完解释部分不能提前结算整个任务。
- [x] 分类不确定不默认要求用户澄清；有合理解释时先调查。只有不同解释会显著改变目标或权限时才提问。
- [x] 分类升级不扩大权限；用户的只读限制、Plan 边界继续生效。显式要求“只解释”也不能因模型误操作而被扩大成实现授权。

验收：“帮我支持 CSV 导出”“请把首页做成深色”进入行动处理；“解释 CSV 导出的原理”“分析最近更新”正常回答；明确行动请求不能仅凭一条 Done 正常结算。

自审：自然语言无法靠规则获得完整正确性。该项应报告已覆盖样本与实际误判率，不承诺彻底消灭所有语义漏判，也不把不确定性全部转成用户审批。

**实施证据：** `classify_intent`、`task_state classify`、宿主工具影响复核；中英文/混合请求与只解释边界已回归。规则和脚本样本通过不代表真实自然语言误判率已测得。

- [x] 保留原始请求及后续修订；验收条件可引用相应输入或需求项，并说明检查目的。该关联供复核使用，不当作语义正确性的证明。
- [x] 将条件来源区分为调用方明确提供、用户明确要求和模型提出。保留现有对操作任务降级、条件替换、需求修订的约束。
- [x] 给现有三类条件标注证明能力：`file_exists` 证明产物存在，`file_contains` 证明文本匹配，`command` 证明具体检查在相应状态运行成功。
- [x] 对明确要求某个文件或产物的结构化输入落实对应检查，已有无关文件不得替代该产物。自由文本中的需求提取依然需要记录其推断性质。
- [x] 对行为修改优先要求针对行为的证据；静态文件条件单独通过时，报告为产物已检查、行为未验证，避免显示没有限定语的“功能已完成”。
- [x] 文档、配置、图片等任务允许适用的产物检查或审阅结果，不强迫所有任务写代码测试；视觉和人工审阅作为后续验证器扩展，不在第一批强行铺开。
- [x] 简单任务自动形成合理条件；不要要求用户逐项审批模型提出的验收标准。复杂、互相矛盾或有实质范围争议的需求才需要澄清。
- [x] 将必需工作项与模型建议的可选工作区分。明确需求不能删除；模型自行提出的额外优化可带理由延后，不能仅因一个可选 Todo 未完成就卡住已完成的用户请求。
- [x] 第一阶段用明确的结构化约束、证明能力和真实行为用例降低弱验收风险。模型复核可作为后续辅助，不能由另一句“检查充分”直接产生成功证据。

验收：要求实现分页时，“README 存在”不能单独产生无条件的功能完成结论；要求创建文档时，合理的文档检查可交付；无测试项目能够说明已验证和未验证内容并正常交付适当结果。

自审：Harness 无法自动证明所有自然语言需求已覆盖。该项提升证据质量与结论准确度，不把新增 `requirement_id` 包装成语义证明，也不要求所有任务都有独立隐藏测试。

**实施证据：** `task_requirements`、`criterion_sources`、`input_id/purpose`、`assurance` 与可选 Todo；纯文档、无测试项目和弱 README 条件均有独立检查。视觉/人工审阅仍为后续扩展，不算本次交付。

## 5. 审批应表达明确授权范围，减少重复打断

**优先级：P1；证据 A/B。**

修改位置：`permissions.py`、`approval/types.py`、`approval/store.py`、`execution/process.py`、桌面审批交互。

- [x] 宿主文件/目录观察不经命令审批；移除仅靠 echo/pwd 等名称的进程豁免。任意程序仍受审批约束，通过明确任务期授权减少重复询问。
- [x] 保持 `allow_once` 的一次语义，不把减少审批实现成偷偷缓存一次授权。
- [x] 增加明确的任务期授权选项：限定当前用户任务 ID、工作区真实路径、具体命令或受控操作、权限模式；不隐含对子任务扩大范围。
- [x] 相同项目检查可由用户明确授权本任务内重跑。若授权绑定检查脚本内容或配置，相关内容变化后必须重新判断；不要把固定 argv 误认为固定执行代码。
- [x] 任务结束、切换目录、权限变化及会话恢复时失效；恢复后除非存在明确持久授权，不自动继承任务期授权。
- [x] 审批卡展示操作、范围、有效期、风险依据和本次为何需要询问。统计请求数、去重后的用户决策数及实际等待时间。

验收：已批准的任务期检查按范围重跑不反复询问；换参数、换目录、换任务或改变受约束脚本后重新判断；一次授权不能变成整会话授权；拒绝后不启动副作用。

自审：减少审批不等于全局放行命令名称。任务期授权必须是用户看得见的选项；真正安全的自动放行依赖受约束能力与执行后端。

**实施证据：** `allow_task` 绑定任务/版本、真实目录、argv、内容摘要、可执行文件和环境；源码变化、模式变化、后续拒绝覆盖旧授权均已测试。审批请求/后端决策/等待时间分别计量，模拟数据不能代表真人负担。

## 6. 根据失败原因选择恢复动作，避免一律停下或一律重试

**优先级：P1；证据 B，部分行为沿用旧实现，并非均为本次新增回归。**

修改位置：`core/agent_loop.py`、`core/loop_engine.py`、`core/verification.py`、`llm/anthropic_adapter.py`。

- [x] 用结构化原因驱动策略，区分可重试模型传输失败、输出截断、验证失败、缺少验收、等待用户、权限拒绝、预算耗尽和未知副作用。
- [x] `max_tokens` 等截断响应中的工具继续不派发；若预算允许，可丢弃不完整操作并有限次重建请求或续行。不能执行拼接后未完整校验的工具参数。
- [x] 用量缺失且金额预算无法核算时，继续遵守停止策略；不能为了自动恢复绕过费用不确定性。
- [x] 缺验收条件先补条件，验证失败先定位失败；不要把两种情况都归为同一句“修复后重试”。
- [x] 防空转除失败输出外观察实质进展，例如相关代码版本、失败集合、尚未完成的验收项；仅改日志、Todo 文案或无关文件不算进展。
- [x] 即使存在进展，也保留总请求、总时间和修复次数上限；按错误指纹和任务修订号管理重试，不无限重置预算。
- [x] 用户取消、权限拒绝和必答问题继续明确暂停；不得用重试绕过拒绝，也不得编造用户回复。
- [x] 恢复先服务当前明确授权的任务，不新增跨进程无限续行或无人值守驱动器。

验收：一次可恢复截断可在限制内继续；重复截断停止并说明原因；代码已有实质进展时不因同一表面错误过早停止；真正空转最终停止；未知副作用和取消不得自动重放。

自审：有进展不等于获得无限执行权。恢复机制应提高有界执行的完成率，不能靠放宽所有上限制造表面成功。

**实施证据：** `modelRecoveryLimit`、结构化重试原因、相关产物/条件进展摘要；截断不派发工具，日志变化不算进展，未知用量跨轮保留，取消和未知副作用继续阻止重放。

## 8. 评测必须同时衡量效果、误报与用户负担

**优先级：立即建立协议；真实对照在核心修复后执行。**

修改位置：`evals/cases.py`、`evals/worker.py`、`evals/runner.py`、`evals/__main__.py`、`docs/task-evaluations.md`、CI。

- [x] 增加自由中文任务、混合请求、纯分析、文档任务、无测试项目、中途改需求、真实进程中断和多个未知操作等场景。
- [x] 保留工作目录外的独立检查和保护文件检查。任务成功由外部行为证据判定，不能用内部 `complete` 自我评分。
- [x] 增加误报完成率：内部宣称完成而外部验收失败的比例，明确分母；任务失败率与误报完成率分别报告。
- [x] 增加正常问答被错误阻塞率、恢复成功率、审批请求数、用户决策数、澄清次数、成本、耗时与请求次数。

- [x] 建立固定协议的版本配对比较工具，校验共同样本/配置并展示逐样本结果与探索性区间；前后 smoke 原始结果已保留。
- [ ] 使用付费真实模型按固定协议重复配对运行，报告收益、波动、费用和实际人工负担；本轮尚未运行，不预设提升幅度。
- [x] 基础设施错误单独报告数量和原因，不计为通过；不能静默丢掉不利样本。无法发布完整成功率时明确说明缺失。

## 9. 后续优化：并发预算与真实限制后端

**优先级：P2；证据 B/C，不阻塞上述正确性修复。**

修改位置：`execution/runtime.py`、`execution/model_requests.py`、`sandbox/`、配置与平台测试。

- [x] 测量共享预算锁持有整个请求期间对并发子代理的影响。未证明实际瓶颈前，不把它当作已复现的性能退化。
- [x] 无金额上限时，仅在请求额度分配和用量记录时持锁；并发不会超分请求槽位。
- [ ] 有金额上限时采用原子费用预留、结算和释放；当前继续使用已验证的串行核算，不伪称已实现并发费用预留。
- [x] 请求异常、取消、流关闭及缺失用量都要正确结算；价格和 token 仍为估算时继续说明其边界。
- [ ] 平台后端先完成一个实际可用的受限执行路径，明确文件、网络、子进程和平台支持范围；按真实能力分别声明，不能把仅覆盖部分资源的后端标成全隔离。
- [ ] Windows 与其他平台分别验证路径别名、符号链接、子进程及限制逃逸；后端不能执行所请求的限制时继续拒绝降级。

验收：并发不会超分请求额度或复用预留费用；取消等待不死锁；预算收益有测量结果；后端行为通过目标平台测试，缺失能力在 UI 与配置中如实显示。

自审：两项都是有价值但独立的工程工作。不能为“更高级”同时重写预算、验证、状态机及所有平台隔离。

**实施证据：** 合成预算锁和本机快照测量已归档。无金额上限的并发请求已优化；有金额上限仍串行。原生受限后端及跨平台逃逸验证尚未完成，限制能力不足继续拒绝降级。

## 建议拆分与落地顺序

| 批次 | 内容 | 交付条件 |
| --- | --- | --- |
| 0 | 最小复现、隔离测试配置、评测协议与基线 | 问题可重复，比较方式固定 |
| 1 | 最终状态验收、任务识别、证据能力与报告 | 修复三个已复现的完成判定问题；正常问答与产物任务可交付 |
| 2 | 恢复观察、按调用核对、明确任务期授权 | 观察不中断，未知结果不被误清空，授权范围不扩大 |
| 3 | 原因驱动的有限恢复与防空转 | 可恢复失败能够继续，取消、拒绝和预算限制仍可靠 |
| 4 | 真实模型前后对照、报告和文档 | 同时公开收益、成本、人工介入和样本限制 |
| 后续独立批次 | 并发预算优化、首个平台限制后端 | 各自具备测量或平台证据后再推广 |

每批配套相应 UI/协议和持久化兼容，不把所有界面修复拖到最后。评测仪表尽早建立，不等全部开发完成才开始计量。

## 自审后的保留与删除决定

保留：版本化编辑、原子发布、持久输入、任务修订、共享预算、取消、未知副作用记录、只读与 Plan 边界、拒绝后的不执行保证。

没有纳入本轮：每条消息额外调用分类模型；所有验收条件逐条找用户审批；强迫文档和问答写测试；把任意命令标为只读即可放行；自由文本清空所有未知调用；预算耗尽自动续费；无限目标续行；未经测量就全量重构并发和平台后端。

最终发布应同时满足：已复现的错误完成用例被修复；正常问答无新增阻塞；拒绝和取消边界无回归；可恢复任务有可用路径；真实对照结果没有把成本或人工负担转移出去后再声称提升。统计证据不足时发布工程改进，但保留“任务成功率收益尚未证实”的结论。
