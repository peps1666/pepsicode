- **P3：** 有意保留的能力边界，可作为独立后续工作，不等同于已发生故障。

- **源码确认：** 当前实现或配置直接体现的事实。
- **待测量：** 风险或改进机会已识别，实际影响仍需验证。

## ISSUE-001：验收快照排除实际被验证的代码

**位置：** [workspace_state.py](../pepsicode/core/workspace_state.py)、[task_verification.py](../pepsicode/core/task_verification.py)。

**现象与原因：** 工作区摘要固定排除 `build`、`dist` 等目录，仅为明确列出的产物和文件条件补充路径。命令条件实际读取这些目录中的代码时，相关文件不一定被纳入摘要。此时“验证前后摘要一致”并不能证明被执行代码保持不变。

**复现：**

1. 创建 `build/value.py`，内容为 `VALUE = 42`。
2. 任务要求实现计算行为，原始请求不指定这个路径；验收只使用命令条件。
3. 第一条验收命令运行 `runpy.run_path('build/value.py')` 并断言 `VALUE == 42`，成功退出。
4. 第二条验收命令将同一文件写为 `VALUE = 0`，也成功退出。
5. 实测最终状态为 `complete`，证明级别为 `behavior_checked`。

**期望：** 后续命令改变实际被验证的代码后，先前成功证据失效，不能提交完成判定。

**影响：** 最终状态绑定只对快照覆盖的输入有效；上次修复的“后续命令破坏旧绿色结果”在排除目录中仍存在。

**修复方向：** 明确验证输入范围，对执行所依赖的源码、测试、配置和相关生成物进行覆盖或隔离；不能仅凭目录名称判断内容可忽略。完整依赖无法推断时，应如实限制证明范围。不得直接取消所有缓存排除而制造无穷重验。

**具体解决方案与实施步骤：**

1. 在 `workspace_state.py` 中区分宿主运行数据、可再生缓存和可能参与验证的项目内容。第一批取消对 `build`、`dist`、`release` 的无条件整目录排除，避免将实际执行代码误当缓存；保留经确认不会作为本轮验证输入的缓存排除，并记录排除原因。
2. 为本轮验证建立由宿主管理的输入清单，覆盖项目源码、测试、配置及准备阶段生成的相关产物。显式输入优先于默认排除，支持目录递归、缺失路径、新增和删除；清单与排除规则摘要写入验收记录。模型可以建议输入路径，不能自行缩小宿主已确定的范围。
3. 将生成代码、构建与 fixture 准备放到 `verificationPreparationCommands`；准备完成后计算基线，随后执行项目检查和任务检查。比较最终内容摘要，变化时清空本轮证据并返回 `verification_state_changed`，在已有预算内有限重验。
4. 对 `node_modules`、虚拟环境、外部服务等无法完整覆盖的依赖记录证明边界。不能仅凭 argv 自动推断所有运行时依赖，也不能把“工作区摘要相同”描述成整个运行环境不变。允许输出带范围说明的结果，避免把所有普通任务都变成无限等待。
5. 后续再接入受限制的验证副本或文件访问追踪。副本必须包含未提交和未跟踪的任务改动；没有真实隔离能力时，复制目录本身不能被称为只读沙箱。新保证与旧的内容摘要保证分别报告。

**落地约束：** 先修覆盖遗漏，再做 ISSUE-009 的性能优化；不能用更激进的排除规则抵消新增检查开销。第一阶段仍明确不抵御恶意进程修改后还原文件的竞争行为。

**验收标准：**

- [x] 上述轨迹不再产生有效的 `complete/behavior_checked`。
- [x] 覆盖 `build`、`dist` 中实际参与行为检查的输入。
- [x] 覆盖相关文件新增、删除和同时间戳内容变更。
- [x] 正常缓存写入不会导致无限验证。

**本轮实施：** `workspace_state` v2 取消 build/dist/release 排除，支持宿主 `verificationInputs` 递归目录及缺失路径，显式输入仅扩大范围，策略摘要随证明持久化。构建目录的后续破坏命令返回 `verification_state_changed`。回归见 `test_project_issues.py::test_issue001_*` 及原有内容摘要测试。限制副本/访问追踪尚未接入，依赖缓存与外部服务的证明范围仍明确保留。

## ISSUE-002：文件名提及被错误提升为产物存在约束

**位置：** [task_control.py](../pepsicode/core/task_control.py) 的 `artifact_requirements()`，以及任务验收中的 `required_artifacts` 检查。

**现象与原因：** 行动请求中识别出的文件名被加入 `required_artifacts`。虽然来源标为 `inferred`，后续仍硬性要求文件存在，没有区分输入、输出、删除对象、参考对象或禁止修改对象。

**复现：**

1. 准备 `old.py`。
2. 请求：`Implement the migration from old.py to new.py; remove old.py.`
3. 执行后 `new.py` 存在、`old.py` 已删除，符合要求；验收命令也明确检查这两个事实。
4. 实测任务仍为 `incomplete`，原因是 `Required artifact is absent: old.py`。

**期望：** 删除和重命名任务允许旧文件缺失；只有明确需要交付或保留的对象才应受到存在性约束。

**影响：** 正确完成的任务被阻塞；代理可能为了满足 Harness 而重新创建用户要求删除的文件。

**修复方向：** 将文件角色与来源分开建模。低置信度推断应可审计地纠正，不得让模型借此删除用户明确要求。需要支持不存在、迁移等相应检查，而不是仅增加更多文件名关键词。

**具体解决方案与实施步骤：**

1. 将 `artifact_requirements()` 的输出改为文件提及候选，不再把所有正则匹配直接写成强制存在约束。候选记录路径、输入来源 ID、角色、推断依据及是否已确认。
2. 最少区分 `input`、`output`、`delete_target`、`protected`、`reference`。只有确定的输出或明确保留对象才形成存在性要求；输入和参考对象不要求交付时仍存在。
3. 在验收条件中增加建议的新类型 `file_absent` 和 `file_unchanged`。前者检查删除目标不存在，后者对比受保护对象的基线内容版本。迁移条件组合检查新文件及旧文件缺失，是否要求内容一致由具体用户需求决定。
4. 扩展 `task_state` 的角色纠正与需求修订接口：允许纠正来源为 `inferred` 的错误角色并记录原因；改变来源为用户或调用方的明确约束，必须关联真实的新指令，不能用一条模型解释直接删除。
5. 调整提示、报告与旧会话读取。旧版推断来源的 `required_artifacts` 恢复为待复核提及；调用方明确提供的产物约束继续保留。角色变化使相关旧证据失效，但不删除历史记录。

**落地约束：** 普通重命名不增加一次用户确认；模型依据原始要求即可纠正明显的推断错误。存在实质范围冲突时才澄清。

**验收标准：**

- [x] 删除、重命名、迁移任务正常完成。
- [x] 参考文件、反例文件和禁止修改文件不自动成为新增交付物。
- [x] 用户明确要求生成的文件仍不能被无关 README 替代。
- [x] 推断纠正有来源记录，用户明确约束不会被静默放弃。

**本轮实施：** 文件角色集中在 `core/file_contract.py`，文件名默认是可审阅提及，明确输出才形成存在约束。新增 `file_absent`/`file_unchanged`，后者使用执行前宿主基线，缺基线不能通过；`task_state correct_files` 用精确任务版本和理由审计纠正，显式约束的变更要求已交付的新输入。旧推断迁移为待复核提及，明确产物和历史记录保留。回归覆盖迁移、否定生成、保护文件被修改、角色纠正、旧记录及缺失产物；自由文本角色推断仍有语义局限。

## ISSUE-003：新用户指令不能替换旧的只读意图

**位置：** [task_control.py](../pepsicode/core/task_control.py) 的 `admit_steering()`、[task_state.py](../pepsicode/tools/task_state.py)、[tooling.py](../pepsicode/tooling.py)。

**现象与原因：** 新指令可将任务 `kind` 改为 `change`，但旧的 `classification.read_only_request` 和锁定信息未同步修订。分类工具及修改工具随后继续执行旧限制。

**复现：**

1. 初始请求为“只解释如何修改首页，不要修改代码”。
2. 当前任务接受运行中指令：“现在修改首页，添加深色主题”。
3. 实测任务 `kind=change`，分类信息却仍为 `kind=answer, read_only_request=true`。
4. 模型修正分类被拒绝，写文件返回 `User requested explanation only; mutation was not executed`。

**期望：** 真实用户的后续指令可以修订任务意图；更新后仍服从独立的权限模式、Plan 边界与审批规则。

**影响：** 持久输入虽然已被接受，执行策略仍使用旧意图，导致用户授权后的工作不能继续。

**修复方向：** 在接受和交付新指令时，一致更新任务类型、分类约束、需求来源及版本。区分“用户改变要求”和“模型自行扩大权限”，不能靠全局删除只读保护修复。

**具体解决方案与实施步骤：**

1. 提取统一的用户指令应用函数，由 `steer` 交付和等待回复后的任务续行共同调用；不要分别只修改 `kind`。以输入 ID 去重，恢复后重复交付不得重复升级版本或扩大范围。
2. 将任务分类改为带来源的当前意图投影：原始要求、后续指令及修订依据保留历史，当前 `kind`、`read_only_request`、锁定来源和文件角色一起更新。
3. 新指令收紧范围时，接收后立即阻止新的相关修改；放宽范围时，必须等指令真实交付并完成任务状态更新后才生效。已启动操作只按现有取消机制停止，不承诺回滚已发生副作用。
4. 在同一控制状态事务中更新已交付修订号，清空验收证据，使受影响条件待复核，并失效旧任务期授权。快照或持久化失败时，不发布半更新状态。
5. 模型分类工具仍不能解除真实用户限制。明确区分任务意图与运行权限：用户把解释改为实现，只影响任务契约；只读权限模式或 Plan 模式仍需通过原有入口处理，不能自动切换。

**落地约束：** 验证“无关补充不会取消原只读限制”“后续明确授权只覆盖相应目标”“多条互相冲突的新指令按已接受顺序生效”。不能简单规定任何较新的输入都覆盖全部旧约束。

**验收标准：**

- [x] 上述新指令交付后，在原有权限允许范围内可以修改。
- [x] 反向变更为“停止修改，只分析”也及时生效。
- [x] 模型自身的分类操作不能解除用户限制。
- [x] 权限只读或 Plan 模式不会因任务意图变化而被绕过。

**本轮实施：** `core/task_intent.py` 统一队列接收、实际交付及澄清后的续行；收紧立即生效，放宽等待真实交付。消息树和意图同次保存，失败整体回滚；输入 ID 去重、移除队列输入、无关补充及引用旧产物均有回归。原任务期授权失效；Full Access 下实际写入可成功，Read Only/Plan 仍拒绝。用户改为只分析后结束为 answered，并不接受旧实现条件为已完成。模型自身仍不能解除用户只读限制。

## ISSUE-004：真实任务效果缺少配对证据

**位置：** [评测说明](task-evaluations.md)、[改造验证记录](../benchmarks/results/harness-improvement-20261026/README.md)。

**已确认事实：** 现有归档包含工程回归、模拟服务、smoke 和微基准。前后 smoke 各一次，模型请求数均为零，真实模型成功率差值为 `null`。文档明确说明没有运行付费真实模型实验。

**影响：** 可以确认机制存在及部分故障轨迹被修复，但无法量化真实任务成功率、误报完成、成本及人工介入的变化。测试数量和清单完成率不能替代这些结果。

**后续要求：** 使用同任务、同模型设置、同预算和外部独立检查器，分别比较预置验收与模型自行定义验收。纳入普通编码、分析、文档、删除迁移、中途改需求及中断恢复；同时披露失败、基础设施错误、成本和用户干预。

**具体解决方案与实施步骤：**

1. 在 `evals` 协议中固定前后提交、模型 ID、思考设置、工具集合、限制、审批策略、样本摘要和评测器版本。旧版接口差异由评测侧适配，不能给旧版补上新版 Harness 再作比较。
2. 建立两条独立轨道：`preset` 由调用方提供验收，`model` 由代理自行定义验收。两条轨道都使用工作目录之外的相同检查器判断任务效果，内部 `complete` 仅用于统计误报和误阻塞。
3. 先运行离线回归和 smoke 检查接线；随后对修复后的候选进行小规模真实模型配对试验，每个样本重复运行并保留逐次结果。样本量和可接受费用在实际发起实验时明确，不能把试验次数包装成统计充分性。
4. 同时报告外部任务成功、内部错误完成、外部已通过但内部未完成、正常问答误阻塞、恢复成功、请求数、费用及耗时。审批请求、真正的人类决策和模拟审批分开统计；没有真人参与的实验不能宣称降低了实际人工负担。
5. 将基础设施失败、未知用量、缺失 worker 输出单列，保留完整样本计划。发布成对差异、区间和限制说明；数据不足时保留“效果尚未证实”，不输出预设的提升幅度。

**落地约束：** 本文件不启动任何付费评测。CI 继续只跑离线检查；真实评测沿用明确发起的执行方式。

**验收标准：**

- [ ] 原始协议、逐任务结果与前后版本身份可复核。
- [ ] 单列误报完成、误阻塞、恢复成功和人工介入。

**修复方向：** 在现有回归保护下逐步提取输入调度、任务状态转换、事件投影及资源清理；优先统一已经重复的行为。避免同时重写终端、服务端与代理循环。

4. TUI 按输入调度、屏幕投影和运行生命周期逐块提取；服务端按会话服务、RPC 分发和事件投影拆分。资源拥有者与关闭顺序保持明确，不能拆出失去所有者的后台任务。
5. 桌面 store 先提取纯事件转换和历史归并函数，再按连接、队列、任务和分支组织状态。以真实调用 ID 配对，并继续拒绝旧连接和旧请求覆盖新状态。
6. 每个 PR 只迁移一类职责，不混入协议语义变化；对应回归通过后再移除旧路径。若无法说明重复规则或维护成本如何减少，暂缓该次拆分。

## ISSUE-009：内容摘要的规模开销需要继续评估

**本轮实施：** 执行快照记录每次扫描原因、数量、读取字节、耗时与总次数。遍历复用 scandir 类型结果、同一次 manifest 内去重，内容仍逐次 SHA-256，不跨扫描缓存。可复现脚本 `scripts/benchmark_workspace_state.py` 在相同机器/输入下比较 af533e9：1 万个小文件中位数 11156 → 7922 ms；真实源码包 156 → 109 ms。源码包的单任务探针 5 次扫描共 546 ms、1 次模拟审批；没有执行真实模型，不能据此宣称减少实际人工负担。仓库根的历史成品超过 512 MiB 时按上限拒绝，未靠重新排除源码获得收益。实际模型交互规模和可靠跨扫描失效机制仍待后续测量。

**位置：** [workspace_state.py](../pepsicode/core/workspace_state.py)、[权限授权键](../pepsicode/permissions.py)、[快照微基准](../benchmarks/results/harness-improvement-20261026/snapshot-benchmark.json)。

**已确认事实：** 归档中，1 万个小文件共约 2.88 MB，单次内容摘要中位数约 10.17 秒。验收前后各计算一次摘要，任务期命令授权键也会计算工作区状态。该结果来自特定 Windows 环境，不能直接推广为所有机器的用户延迟。

**影响：** 较多文件的仓库可能产生额外等待；将授权绑定完整工作区也可能因无关内容变化而重新询问。实际交互开销与审批次数仍需测量。

**具体解决方案与实施步骤：**

1. 为摘要和授权键生成增加计量：文件数、读取字节、每次耗时、每任务调用次数，以及因何重新计算。先确定时间主要消耗在遍历、路径解析、内容读取还是重复扫描。
2. 合并同一已封存验证边界内的重复请求，复用同一份不可变 manifest；有新工具修改、外部变化、不确定性或新的验证阶段时重新校验。不同调用之间不能无条件复用旧摘要。
3. 优化遍历、重复路径解析和内容读取；增量缓存只有在可靠的失效机制支持下才用于正确性判定。mtime、文件大小或不完整 watcher 不能单独证明内容未变，watcher 丢事件时回退完整扫描。
4. 验收范围与授权范围分别设计。验证应覆盖实际被验证输入；精确命令授权可在明确依赖可识别时绑定更小的宿主输入集合，无法确定依赖时保留保守规则，不能让模型随意声明“无关文件”来复用授权。
5. 对大仓库支持明确的项目/包范围和进度反馈；缩小范围时展示哪些需求不在本次证明内。扫描超限、取消和不可读文件均返回可操作原因，不无限重试。
6. 使用相同机器和相同样本比较耗时分布，同时回跑 ISSUE-001、同时间戳覆盖、新增删除和外部修改用例。只报告已测得的收益。

**验收标准：**

- [x] 覆盖真实源码工作区和 1 万文件样本，记录单任务摘要次数、耗时与模拟审批次数；实际交互分布待测。
- [x] 优化不依赖 mtime 作为唯一内容依据。
- [x] 不能通过忽略实际参与验证的源码获得性能收益。
- [x] 对范围过大、输入不可读等情况提供可操作说明，并避免无限扫描。

## 已知边界：ISSUE-010 至 ISSUE-012

### ISSUE-010：操作系统受限执行后端未实现

当前 LocalSandboxBackend 不提供内核级文件或网络隔离；默认是应用层审批，选择其无法执行的限制模式会拒绝启动。该行为已如实记录，不能当作隔离已经完成，也不应通过直接降级运行来补齐。

后续按目标平台实现、分别声明文件/网络/子进程限制范围并进行逃逸验证。是否作为发布阻塞，应取决于该版本承诺的执行模式。[执行边界](harness-boundaries.md)

**具体解决方案与实施步骤：**

1. 定义后端能力表和执行策略，分别描述文件读取、文件写入、网络、子进程、环境继承及资源清理。审批结果与隔离能力分开记录，不能用“已批准”替代“已受限”。
2. 先选择一个目标平台完成最小实现和验证；Windows 进程树管理、受限令牌或 Job Object 不能单独被当作完整文件/网络隔离。若选择容器或虚拟化后端，明确其安装条件、挂载范围及额外权限。
3. 将实际受限 argv 与策略交给现有进程入口，后端启动前验证所请求的能力是否存在。不可执行的限制继续拒绝启动，不能降级到宿主直接执行。
4. 验证工作区外写入、路径别名和链接、子进程继承、网络访问、退出清理及宿主敏感环境隔离。清理只针对本次执行拥有的资源。
5. 在设置、审批和报告中显示实际 enforcement 及平台限制；新后端先作为明确可选项交付，通过验证后再考虑默认策略。

**验收标准：**

- [ ] 请求的限制真实作用于最终启动的程序及其子进程。
- [ ] 能力缺失、初始化失败和无法验证的策略不会静默降级。
- [ ] 平台测试证明的范围与 UI、文档声明一致。
- [ ] 取消、超时和会话关闭不会清理无关进程或文件。

### ISSUE-011：有金额上限的请求仍串行核算

无金额上限时已允许请求并发；有金额上限仍持锁串行，尚无并发费用预留。此处是已知吞吐边界，没有证据说明当前会重复花费余额。

后续先测实际影响，再实现原子预留、结算与异常处理，不能为提高并发而削弱预算核算。[实施记录](harness-improvement-plan.md)

**具体解决方案与实施步骤：**

1. 测量串行等待对真实并发子任务的影响，区分提供商延迟、任务依赖和预算锁等待。若收益不明显，可保留现有安全实现。
2. 为每次请求建立唯一 reservation ID。在共享锁内检查请求次数及“已花费估算 + 在途预留 + 新请求保守估算”，额度不足则等待或明确拒绝；锁外执行网络请求。
3. 完成后在锁内按提供商实际用量结算并释放预留。重试和摘要请求都经过同一入口；同一响应不能被执行器和适配器重复记账。
4. 取消或网络异常后，只有能够确认未发生收费的请求才释放相应估算；收费结果不明时保留不确定状态并阻止继续花费，不能当作零成本。
5. 等待额度的请求持续观察取消和截止时间；预留本身不授予额外请求次数。保留串行路径作为兼容或诊断选择。

**验收标准：**

- [ ] 并发请求不能重复使用同一笔可用估算余额。
- [ ] 异常、重试、关闭流及重复完成回调不会漏算或重复结算。
- [ ] 取消等待和父子任务取消不死锁。
- [ ] 继续将本地费用估算与供应商精确账单区分，不能承诺不存在的精确硬上限。

### ISSUE-012：未知结果下没有受控 Git 状态查询

当前已有文件和目录观察、逐调用核对；普通 Git 命令仍受未知结果阻塞，避免借 Git 配置或外部辅助程序扩大执行能力。恢复能力因此尚未覆盖所有仓库核对场景。

后续需要固定参数、处理可执行辅助程序及配置路径、验证目录边界后再提供专用观察入口。任意 Shell 不能自行声明只读而获得豁免。[恢复方案](harness-improvement-plan.md)

**具体解决方案与实施步骤：**

1. 增加宿主拥有的仓库观察操作，第一版只提供固定的状态查询，不暴露任意 Git 子命令、任意配置参数或 Shell 字符串。
2. 固定并验证 Git 可执行文件、真实工作目录和参数；处理 pager、fsmonitor 等可能启动辅助程序的配置。若后续支持 diff，还需处理 external diff、textconv 等机制。无法证明受控的路径继续使用现有审批或文件级观察。
3. 在受控环境中运行，限制输出、超时及子进程；验证仓库根、工作树及 Git 元数据边界，不假设用户提供的 `.git` 文件天然可信。应用级约束不能冒充操作系统隔离。
4. 查询结果生成宿主 observation ID，关联 recovery revision、命令身份及状态摘要。核对某个未知调用时引用该记录，状态已变化则重新观察。
5. Git 状态只证明仓库观察结果；远端 push 是否成功、外部服务是否提交等仍需对应远端证据。不能因本地工作区干净就清除所有未知操作。

**验收标准：**

- [ ] 未知结果期间能够执行经过审查的固定观察操作。
- [ ] 项目 Git 配置不能借此启动任意辅助程序。
- [ ] 伪造或过期 observation 不被接受，未引用的未知调用继续保留。
- [ ] 普通命令和外部修改不会自动获得观察豁免。

## 方案自审与实施原则

- **每个问题都有对应方案：** ISSUE-001 至 ISSUE-012 均包含具体实施步骤；前三项先建立失败回归，再修改实现。

- **避免增加无意义阻塞：** 不要求普通任务逐条审批验收，不强制问答写测试，不把所有文件提及变成必须存在，不把分类不确定一律退回用户。
- **保留已有边界：** 不解除只读/Plan、不重放未知副作用、不把一次批准偷偷扩展成会话许可，也不为并发绕过预算不确定性。
- **兼容与回滚：** 新契约字段和条件类型需要持久化版本及迁移；旧记录保留原始证据。新后端、预算并发等能力独立交付，出现问题可退回原有路径；正确性修复不能回退为原先的错误完成判定。
- **按批交付：** 每批只改一类核心行为，配套协议、客户端和回归。文档中的方案名称、字段及条件类型均为建议，实施前须结合实际接口确定，不能将本文件当作已经存在的 API 文档。
