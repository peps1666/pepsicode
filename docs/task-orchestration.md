# 用户任务的生命周期与验收

这次改动参考了本机 dsh 的输入、轮次、目标与续行边界，沿用 Pepsicode 的 Python 执行器和有界验证循环。源码比较和改造前的离线探针见[审查记录](task-orchestration-review.md)。

## 从用户输入到任务结束

1. 每条用户输入有稳定的来源 ID。运行中的 `steer` 修改当前任务；`follow_up` 在当前任务通过验证后作为下一个独立任务执行。
2. 用户任务有独立的 ID、修订号、目标、验收条件和状态。一次用户任务可能经历多次模型请求、工具批次和验证重试；执行轮次结束不等于任务完成。
3. 新指令一经队列持久化接受，就增加当前任务修订号并清空旧证据。模型收到指令后才更新已交付修订号。验证必须对应同一个、已交付的修订号。
4. 项目回归检查和任务验收分别记录。只给计划、项目测试全绿、无文件变更、模型输出“完成”都不能替代操作类任务的验收条件。
5. 验收失败沿用有界修复：`maxIterations` 限制总轮数，`verificationNoProgressLimit` 限制重复失败；同时受执行取消、请求预算和费用预算约束。达到限制保持未完成。

任务类型包括 `answer`（解释、评审等回答）、`change`（实现或修改）和 `operation`（执行操作）。入口用文本规则初判，并记录原始输入、调用方指定类型及推断来源。所有任务在正常模型请求中获得任务视图，模型可用 `task_state classify` 携带理由纠正不确定的规则判断，无需额外分类请求。明确的操作类型和已识别的明确行动请求被锁定；“只解释”等限制不能通过分类升级变成执行授权。规则仍可能误判，覆盖样本不代表真实误判率已测量。显式验收条件即使用于回答类任务也必须检查。

## 可复核的验收条件

真实用户的新指令通过统一的 `task_intent` 投影修订当前意图，保留原始来源和历史。收紧为“停止修改，只分析”在接收时立即阻止新的修改；放宽为实现则等到消息和新意图在同一次会话保存中提交后生效。输入 ID 去重，撤回的待交付输入不会扩大范围，无关补充或“继续”不会取消旧限制。用户明确改为只分析后可结束为 `answered`，不将未做的旧实现宣称为完成。任务意图变化不会切换只读或 Plan 权限。

`task_state` 始终向主代理提供。`inspect` 返回任务和待回答问题；`define` 必须携带准确的 `task_id` 和 `revision`，只允许追加条件。条件包括：

| 条件 | 检查内容 | 证据 |
| --- | --- | --- |
| `file_exists` | 工作区内指定文件存在 | 路径、内容版本 |
| `file_contains` | 文件包含指定文本 | 路径、内容版本、是否匹配 |
| `file_absent` | 指定文件不存在 | 缺失版本；后续重新出现使证据失效 |
| `file_unchanged` | 与任务执行前宿主记录的内容版本相同 | 基线与当前版本；没有基线时不能通过 |
| `command` | 指定 argv 的进程成功退出 | argv、退出码、输出摘要与哈希 |

文件条件必须使用工作区相对路径。命令条件经过已有命令权限、Hooks、执行日志和取消路径，单条超时 30 秒。Python 字节码缓存按验收隔离，避免重复检查执行旧缓存。验收命令不会因为写在条件里而获得额外权限。

更新条件采用修订号比较；旧版本写入被拒绝。新用户指令使旧条件需要重新确认，不能直接沿用旧证据。若需求确实变化，`revise` 必须引用最新真实输入的 `instruction_id` 并说明原因，保存旧条件与修订依据。单纯“继续”不授权删除原条件。修改后的条件仍由模型解释用户意图，Harness 不能证明替换条件完整表达了用户的新要求。

一次验收生成 `acceptance_run_id`，将项目回归和任务条件绑定到同一任务版本、条件摘要、需求摘要与工作区内容摘要。准备阶段可用 `verificationPreparationCommands` 执行生成代码或 fixture 的命令；准备结束后才开始收集成功证据。最终在控制锁内复核内容、版本、必答问题、必需 Todo 和未知副作用。任一命令改变被验证输入，之前的绿色结果整体失效，返回 `verification_state_changed` 并在既有轮数上限内重验。

默认摘要读取源码、测试和配置等文件内容，跟踪新增和删除，不依赖 Git HEAD 或时间戳。`build`、`dist`、`release` 已纳入默认范围，不能仅因目录名称将执行代码排除。宿主固定排除 `.git`、依赖/虚拟环境、测试缓存、运行日志及宿主会话目录，不采纳模型传入的忽略规则。宿主配置 `verificationInputs`、文件条件及结构化需求只能扩大范围；显式目录递归读取，缺失路径也保留在 manifest 中。输入清单与排除策略摘要写入验收记录，策略变化使旧证据失效。

当前上限为 100000 个文件/目录条目、512 MiB，遍历不可读、范围越界或超过限制会阻止验收并提示选择对应项目/包作为工作区，扫描期间响应取消。仓库根目录包含大量历史 ZIP 等文件时也适用上限，不能静默排除这些目录再声称完整检查。执行快照中 `workspace_scans` 记录每轮扫描的原因、数量、读取字节和耗时；仅在同一次 manifest 构建内去重，不跨调用信任 mtime 或 watcher。完整规则在 `core/workspace_state.py`。

前后摘要是记录范围内的状态关联，不是文件系统或外部世界的事务快照；它不能抵御恶意进程“改动后还原”，未纳入范围的依赖和外部服务也可能变化。需要完整冻结时仍应在隔离副本或具备真实限制能力的后端验证。

条件可以提供 `input_id`、`purpose`；`criterion_sources` 记录调用方、结构化用户要求、规则推断或模型提出的来源。静态条件通过只报告“产物已检查，行为未验证”；命令条件通过报告声明的行为检查通过，不能推广为全部需求已被证明。聊天正文和执行轨迹都显示这种区别，验收数仅计算同一任务版本、验收轮次和工作区摘要的证据。

这些机制保证的是声明的条件确实执行并与相应任务版本关联。**条件是否覆盖全部需求，仍取决于调用方、模型和测试质量。** `file_contains` 适合产物检查；行为变更应优先使用针对行为的命令测试。文件存在和无关测试通过都不能证明功能正确。

程序调用示例（其余参数与原有 `run_verified_turn` 相同）：

```python
run_verified_turn(
    runtime=runtime,
    runner=run_agent_turn,
    model=model,
    tools=tools,
    messages=[{"role": "user", "content": "修复分页边界"}],
    cwd=workspace,
    permissions=permissions,
    task_kind="change",
    acceptance=[{
        "id": "pagination-behavior",
        "kind": "command",
        "argv": ["python", "-m", "pytest", "tests/test_pagination.py", "-q"],
    }],
)
```

WebSocket `turn/run` 同样支持 `task_kind`、`acceptance`、`task_requirements` 和 `answer_to`（问题 ID 数组）。`task_requirements` 格式为 `{"artifacts":["guide.md"],"behavior":false,"source":"user"}`；来源可为 `user` 或默认 `caller`。明确产物必须存在，其他已有文件不能替代；`behavior: true` 还要求针对行为的命令条件。来源由宿主入口设定，模型工具不能伪造。简单的文档/图片等具名产物可自动形成存在条件，仍只证明产物存在。

CLI/TUI/桌面共用这个入口。内嵌调用若要跨进程恢复，应使用 `recording_session(session)` 绑定持久会话；没有会话时只在 runtime 中维护状态。`runtime.taskAcceptance` 可设置调用环境的默认条件，多个不同任务应优先逐次传入 `acceptance`。

## 输入恢复与澄清

文件提及以 `file_mentions` 保存路径、来源输入、角色及推断依据。角色包括 input/output/delete_target/protected/reference；仅明确推断为输出的候选形成存在要求，不再要求迁移源或参考文件在交付时仍存在。`task_state correct_files` 接受 `file_roles: [{"path":"old.py","role":"input"}]` 和 reason，审计纠正推断；用户/调用方明确约束的修改仍须关联新的已交付指令。“出现文件名”及角色推断都不是语义正确性的证明。旧会话中的推断存在约束迁移为待复核提及，明确产物约束继续保留，旧证据留档。

原生入口将队列绑定到 `SessionData.task_control`。输入先落盘，再通知已接受；存储失败会回滚内存状态，调用方收到错误。交付采用 pending → claimed → 写入消息树 → acknowledge：崩溃后未进入消息树的 claimed 恢复为待交付，已进入消息树的输入按来源 ID 去重。

被移除或在停止时尚未处理的输入保存为 returned，界面将其退回草稿。恢复会话不会自动启动模型，也不赋予历史任务无限续行权限。下次显式运行才会继续处理恢复的队列；returned 可再次回显以避免丢失草稿。输入交付去重不等于外部副作用恰好执行一次，未知副作用仍须经过[执行恢复](harness-boundaries.md)核对。

Todo 和问题归属各自会话；子代理使用独立控制状态，不能修改父任务验收。Todo 有稳定 ID、完成状态和所属任务 ID。模型额外建议的可选工作可设 `required: false` 并记录 `reason`，未完成的可选 Todo 不阻塞交付；这不能删除明确需求或验收条件。`ask_user` 默认 `required: true`，任务进入 `waiting_user`；`required: false` 可提出不阻塞的问题。回复一个待答问题时可自动关联；多个待答问题应通过 `answer_to` 明确关联，系统不会用超时编造回答。

未完成任务收到“继续”，或等待澄清时收到回复，会保留任务 ID 并增加版本。普通新任务及 `follow_up` 创建新 ID，旧任务保存到历史。切换对话分支清除当前任务身份；复制或 fork 不复制任务续行身份和 inbox。重新生成同一任务仍必须重新验收，不能继承上一次成功结论。对话分支共用磁盘文件，不恢复历史文件状态。

## 结束原因与防空转

普通与流式模型响应都检查停止原因。`max_tokens`、`pause_turn`、拒答和缺少完整结束事件不会被当作最终成功，也不派发该响应里的工具。已有的空推理输出重试仍有次数上限；非空的半截结果只作为过程保留。流式响应即使出现 `end_turn`，缺少最终 `message_stop` 仍视为不完整。

共享验证循环默认最多重建一次可恢复的截断/传输失败请求，可用 `modelRecoveryLimit` 设置为 0 禁用；重建占用同一个总轮数和请求预算，不拼接工具参数。费用不明、未知副作用、取消和权限拒绝不能借此重放。费用不确定标记随执行状态保存，下一轮也不能把缺失用量当成零。失败原因分别引导补条件、修复检查或稳定验证输入；有任务相关代码/条件的状态时，仅改变日志不会重置无进展计数。

不完整结果携带 `recovery.reason_code` 和 `next_action`。明确“继续处理当前任务”保留原任务身份并重新验收，不直接重放选中的命令。恢复旧会话会重新比较证据的条件和内容摘要；无法证明仍有效时保留历史记录，将当前结果标为待复核。

同一执行范围内，相同任务版本、工具、参数和结果连续重复时，默认在第 3、5、8 次附加提醒，要求改变方法或说明阻碍。可设置 `repeatToolThresholds: [3, 5, 8]`，必须为递增且不重复的整数，最小为 2。提醒不扩大权限，也不替代预算和修复轮数限制。

任务状态为 `active`、`answered`、`complete`、`incomplete`、`waiting_user`、`cancelled`、`blocked`、`unknown` 或 `budget_exhausted`。桌面轨迹显示任务状态和已满足条件数，服务端 `turn/end` 返回任务报告；执行成功与用户任务未完成可以同时存在。

当前实现提供有界重试、显式继续和持久恢复，没有新增跨进程无人值守的无限目标驱动器。离线编排回归见 `tests/test_task_orchestration.py`；真实任务评测入口和 smoke/real 统计边界见[任务评测](task-evaluations.md)。
