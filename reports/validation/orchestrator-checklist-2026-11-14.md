## 失败复现

| 场景 | 运行步骤及结果 |
| --- | --- |
| A25 | 旧协议客户端鉴权连接。返回 cwd、版本和服务代次等字段，没有异步编排能力声明。 |
| B08 | 启临时常驻服务，实际运行 Electron，应用发出 `session/create`。服务在初始化前读 `session_data.session_id`，返回 `-32603`。协议探针复现同一错误。 |
| B10 | 先写人工停止标记，再调用面向服务管理器的 `foreground`。它仍进入服务对象构建，探针随后主动终止。 |
| B12 | 输入新 head 的 CI 失败，再输入同 PR 同检查的旧 head 成功。后者仍进入会话 steer 队列。 |
| B13 | 持久化 `max_requests=1` 而会话上限为 10，观察传给执行入口的仍是 10。 |
| B15 | 走正常协调工具并传入有效 `verificationCommands`。临时 Git 候选集成后验收命令列表为空，返回 `acceptance_failed`。 |
| B16 | 使用本机调用桩，建 PR 的审批路径未调用执行层。首次 POST 响应丢失并且 GET 没找到 PR 时，第二次操作又发 POST。 |
| B17 | 只改变集成 checkout 的未提交文件，保持 HEAD 不变。验收命令对这个文件通过，记录却签给了原 HEAD。 |
| B19 | 闲置会话收到 GitHub 事件并暂存。用同目录重建宿主，已经暂存的事件无法重新入队。 |

## 监督闭环实测

2026-11-16，在 Windows 上从 `run_verified_turn` 进入编排，开启独立 worktree。Worker 在真实本地 Git 仓库和受管进程中执行写入、提交与检查。协调和 Worker 的模型决策由脚本固定，便于判定运行时是否能接续。临时测试仓库未配置远端。

| 场景 | 实际结果 |
| --- | --- |
| Worker 已明确报告失败 | 实际检查返回非零，Worker 调用 `agent_report(failed)` 后正常结束回复。协调者收到的是 `result_ready`；父任务保持未完成。 |
| Worker 提交后重试 | 首次真实检查失败且已提交部分改动。为单独验证重试入口，脚本让该轮以 `max_tokens` 结算成 `failed`。协调者用同一 `work_id` 成功入队新尝试，旧 `expected_head` 检查报告 `Managed worktree repository, branch or HEAD changed`，未启动重试或重跑检查。 |
| 候选单独通过，集成后失败 | 两个候选检查均通过，Git 合并无冲突，集成检查退出码为 1。交付被正确拒绝；`task_retry` 拒绝重试已返回结果的 Worker。另派修复 Worker 时，checkout 从主仓库基线准备，不含两个候选的文件。 |
| 已通过的集成交付与父任务验收 | 集成检查退出码为 0，本地交付记录创建成功。产物存在于集成 worktree，父任务在原工作目录检查该产物，最终状态为 `incomplete`。 |

四个探针均在对应验收断言上失败，复现了待办中的问题。合并失败时拒绝交付这一门禁按预期生效。真实模型监督评测留待常规入口可以跑通这两条路径后进行，现有单 Agent 基准无法衡量这条闭环。
